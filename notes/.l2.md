### Problem statement

The hub's Claude sign-in for cloud loops is refreshed by nothing: the sealed token pair expires and the operator signs in again. Enes agreed (2026-10-17) that the CLI may do the refresh: the hub unseals the pair into a fresh 0700 directory under `<data>/cloud-sign-in/`, the CLI refreshes, the hub reads the rotated pair back, reseals it and deletes the directory. What is not known is which CLI command refreshes without spending a turn. Split out of #864.

### Coupling points

`internal/httpapi` (the login check and sign-in code), the sealed store (ADR-0046), OPERATIONS.

### Seams / ADRs touched

ADR-0058 items 3 and 4, ADR-0044 (login check).

### Proposed shape

Step 1 is a probe against a real login, once the fleet runs the upgraded runtime and Enes has signed in: which CLI invocation refreshes the pair with no turn. Its result goes on this issue. Step 2 is one PR building that path, or, if no command does it, the hub posting to the token endpoint itself.

### Open questions

The probe's answer.

### Out of scope

Docker-hub sign-in (#1080) and revoke (#1082). Per-login refresh under ADR-0060 reuses whatever lands here.
